Implementing Row- and Column-Level Security in Modern Data Warehouses

February 20, 2026

Author: Pravin Darbare
👉 Talk to a Data Services Expert

Why Row- and Column-Level Security Matter

As data platforms scale, access control must move closer to the data. Modern enterprises increasingly rely on:

  • Multi-tenant analytics
  • Shared data products
  • Self-service BI and AI workloads
  • SOC 2 / GDPR / HIPAA compliance

Row-level security (RLS) and column-level security (CLS) allow you to share one governed dataset while ensuring users only see:

  • The rows they're entitled to
  • The columns (or values) they're allowed to view

The key is doing this centrally, dynamically, and auditably.

Column-Level Security in Snowflake

Snowflake implements CLS primarily through masking policies, including dynamic data masking.

1️⃣ Basic Column Masking

Masking policies transform column values at query time, based on role or context.

CREATE MASKING POLICY mask_ssn
AS (val STRING) RETURNS STRING ->
  CASE
    WHEN CURRENT_ROLE() IN ('HR_ADMIN') THEN val
    ELSE 'XXX-XX-XXXX'
  END;

Apply it:

ALTER TABLE employees
MODIFY COLUMN ssn
SET MASKING POLICY mask_ssn;

2️⃣ Dynamic Data Masking (Role-Aware)

Snowflake evaluates masks per query, not by creating copies of data.

Common patterns: Full reveal (admins), Partial reveal (last 4 digits), Hashing, Nulling

CASE
  WHEN CURRENT_ROLE() = 'FINANCE_ADMIN' THEN val
  WHEN CURRENT_ROLE() = 'ANALYST' THEN CONCAT('***', RIGHT(val,4))
  ELSE NULL
END

3️⃣ Tag-Based Masking (Highly Recommended)

This is the scaling superpower. Instead of attaching policies column-by-column: Tag columns (PII, PHI, CONFIDENTIAL), Attach one masking policy to the tag.

CREATE TAG sensitivity;

ALTER TABLE customers
  MODIFY COLUMN email
  SET TAG sensitivity = 'PII';

ALTER TAG sensitivity
SET MASKING POLICY pii_mask;

✅ Benefits: Centralized management, Consistent behavior, Audit-friendly

Row-Level Security in Snowflake

Snowflake uses Row Access Policies to filter rows dynamically at query time.

1️⃣ Basic Row Access Policy

CREATE ROW ACCESS POLICY tenant_filter
AS (tenant_id STRING) RETURNS BOOLEAN ->
  tenant_id = CURRENT_ROLE();

ALTER TABLE orders
ADD ROW ACCESS POLICY tenant_filter ON (tenant_id);

2️⃣ Enterprise-Grade Pattern: Mapping Tables (Do This)

❌ Don't hardcode users or roles into policies. ✅ Use mapping tables.

-- user → tenant mapping
SELECT tenant_id
FROM user_tenant_map
WHERE user_name = CURRENT_USER();

-- Policy example:
EXISTS (
  SELECT 1
  FROM user_tenant_map ut
  WHERE ut.user_name = CURRENT_USER()
    AND ut.tenant_id = tenant_id
)

This: Scales to thousands of users, Simplifies audits, Supports offboarding cleanly

Column-Level Security in Databricks (Unity Catalog)

Unity Catalog brings first-class CLS and RLS into the Lakehouse.

1️⃣ Column Masking in Unity Catalog

ALTER TABLE customers
ALTER COLUMN email
SET MASK
  CASE
    WHEN is_account_group_member('finance_admin') THEN email
    ELSE regexp_replace(email, '.+@', '***@')
  END;

Key notes: Policies are evaluated at query time, Identity comes from account groups, Works across SQL, notebooks, and BI tools

Row-Level Security in Databricks (Unity Catalog)

Unity Catalog supports row filters.

ALTER TABLE sales
SET ROW FILTER tenant_filter
AS (tenant_id STRING) ->
  tenant_id IN (
    SELECT tenant_id
    FROM user_tenant_map
    WHERE user = current_user()
  );

Row filters apply consistently across: SQL, Notebooks, Dashboards, AI workloads

Recommended Enterprise Design (Snowflake & Databricks)

1️⃣ Don't Hardcode Users in Policies

❌ Bad: CURRENT_USER() = 'john@company.com'

✅ Good: Mapping tables — user → tenant / region / department; role / group → dataset entitlements. This is SOC 2-friendly and future-proof.

2️⃣ Prefer RBAC + Policies, Not Copies of Data

❌ Separate tables per team, Separate schemas per tenant

✅ One governed table, Policies enforce access

Why: No data drift, Lower storage cost, Cleaner lineage

3️⃣ Combine RLS + CLS Intentionally

Best-practice combo: Row filters → tenant / region scoping; Column masks → PII, PHI, financials; Views → only when you need a curated contract

Example: Base table: governed + secure; View: business-friendly naming + joins

4️⃣ Explicitly Test Policy Behavior

Treat security like code. Create a test harness: Roles / groups, Expected visible rows, Expected masked vs unmasked values

Example test matrix:

Role Rows Visible SSN Revenue
AnalystTenant-onlyMaskedMasked
FinanceTenant-onlyMaskedVisible
AdminAllVisibleVisible

Run this in CI for every policy change.

Key Takeaways

  • Row- and column-level security should be policy-driven, not data-driven
  • Snowflake excels with tag-based masking at scale
  • Databricks Unity Catalog provides consistent governance across data + AI
  • Mapping tables are the difference between working and enterprise-ready
  • Test security behavior just like application logic

The best data platforms are not the ones with the most data—they're the ones that let you share safely, at scale.
